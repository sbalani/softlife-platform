2. SCHEDULER ARCHITECTURE - NO MOBILE WORK
------------------------------------------

Automated defrost no longer uses Vercel Cron.

Current architecture:

  Supabase pg_cron checks once per minute for due work.
  The check runs inside Postgres and is inexpensive.
  The Supabase Edge Function is invoked only when a schedule is due or an
  active defrost run has reached its next state transition.
  Huaxin credentials and the scheduler token are stored in Supabase Vault.
  The Edge Function owns command attempts, recovery, state transitions,
  status snapshots, audit logs, and alert push delivery.

The mobile agent must not add Vercel cron configuration, call the Edge
Function, or store any scheduler/Huaxin secret.


3. AUTHENTICATION
-----------------

All mobile API calls use:

  Authorization: Bearer <Supabase access token>

All coupon endpoints below are admin-only.

Expected authorization errors:

  401  Missing, expired, or invalid access token
  403  Authenticated user is not an admin

The coupon tab must remain hidden or disabled for franchisees and operators.
The backend still enforces admin authorization if the UI is bypassed.

5. LIST COUPONS
---------------

Request:

  GET /softlife/admin/coupons

Success response:

  {
    "coupons": [
      {
        "couponId": "123",
        "couponName": "Summer promotion",
        "couponType": "0",
        "deviceImeis": "861648083097216",
        "validDay": "30",
        "startTime": "2026-08-14 00:00:00",
        "endTime": "2026-09-13 23:59:59",
        "content": "{...Huaxin coupon content...}",
        "localName": "Malaga",
        "createTime": "...",
        "updateTime": "...",
        "merchantName": "..."
      }
    ],
    "latest_synced_at": "ISO-8601 timestamp or null",
    "stale_machines": 0,
    "machines": [
      {
        "id": "Supabase machine UUID",
        "name": "Display name",
        "imei": "861648083097216"
      }
    ]
  }

Important behavior:

  - coupons comes from Supabase machine coupon snapshots.
  - The response may include expired coupons; it is not an active-only list.
  - deviceImeis is aggregated across machine snapshots.
  - stale_machines indicates missing or stale machine snapshots.
  - machines supplies the UUID values required by create.machineIds.


6. CREATE COUPON
----------------

Request:

  POST /softlife/admin/coupons
  Content-Type: application/json

Discount coupon body:

  {
    "couponType": "0",
    "couponName": "Summer promotion",
    "startTime": "2026-08-14",
    "endTime": "2026-09-13",
    "validDay": 30,
    "totalCount": 10,
    "secondary": 1,
    "machineIds": ["Supabase machine UUID"],
    "localName": "Malaga",
    "money": 1.5
  }

One-cup/free-product coupon body:

  {
    "couponType": "1",
    "couponName": "Free cup",
    "startTime": "2026-08-14",
    "endTime": "2026-09-13",
    "validDay": 30,
    "totalCount": 10,
    "secondary": 1,
    "machineIds": ["Supabase machine UUID"],
    "localName": "Malaga",
    "amount": 1,
    "productPosition": "1",
    "productName": "Ice cream"
  }

Validation:

  - couponType must be "0" or "1".
  - couponName and localName are required.
  - startTime/endTime use YYYY-MM-DD.
  - endTime must not precede startTime.
  - validDay must equal the day difference between startTime and endTime.
  - totalCount must be a whole number from 0 through 100.
  - secondary must be a whole number of at least 1.
  - machineIds must contain valid, stored Supabase machine UUIDs with IMEIs.
  - Type "0" requires money greater than zero.
  - Type "1" requires amount >= 1, productPosition, and productName.

Success response:

  {
    "ok": true,
    "couponId": "123",
    "warning": "optional warning"
  }

warning means Huaxin accepted the coupon but one or more Supabase snapshot
refreshes failed. Treat this as success, display the warning, and refetch.

Validation or Huaxin rejection currently returns HTTP 400:

  {
    "error": {
      "message": "Human-readable reason"
    }
  }


7. LIST COUPON CODES
--------------------

Request:

  GET /softlife/admin/coupons/{couponId}

Success response:

  {
    "records": [
      {
        "code": "...",
        "status": "0",
        "expireTime": "...",
        "createTime": "..."
      }
    ]
  }

Known status values:

  0  Unused
  1  Used
  2  Expired

The records originate from Huaxin. Preserve unknown fields/status values and
display a fallback rather than failing decoding.


8. GENERATE MORE CODES
-----------------------

Request:

  POST /softlife/admin/coupons/{couponId}

Body:

  {
    "num": 5
  }

num must be a whole number from 1 through 100.

Success response:

  {
    "ok": true
  }

Refetch the code records after success.

14. COUPON CODE DISTRIBUTION (ADDED 2026-09-07)
------------------------------------------------

Production platform commit:

  739ced9 Track coupon code distribution

The existing admin code-list response now adds local distribution metadata to
each Huaxin code without changing Huaxin redemption state:

  {
    "code": "provider-code",
    "status": "0",
    "expireTime": "...",
    "createTime": "...",
    "distributed": false,
    "extraInformation": null,
    "metadataRevision": null
  }

`status` remains the provider's unused/used/expired state. `distributed` only
records whether staff gave the code to someone. Never derive either field from
the other.

Update endpoint:

  PATCH /api/softlife/admin/coupons/{couponId}
  Authorization: Bearer <Supabase access token>
  Content-Type: application/json

Body:

  {
    "code": "provider-code",
    "distributed": true,
    "extraInformation": "Optional recipient or handoff note",
    "expectedRevision": null
  }

Send `expectedRevision: null` when the returned `metadataRevision` is null.
After a successful update, send the returned revision on the next edit:

  { "ok": true, "revision": 1 }

The optional information field accepts an empty string and is limited to 1,000
characters. The backend verifies that the exact code still belongs to the
Huaxin campaign before saving. Concurrent stale edits are rejected with a
message instructing the client to reload; do not overwrite or retry them
automatically.

Recommended native behavior:

  - Show provider status, a separate Given out checkbox, and optional text.
  - Save the checkbox immediately and roll it back if the request fails.
  - Save text explicitly so typing does not issue a request per character.
  - Disable both controls while that row is saving.
  - Replace the row's metadataRevision with the returned revision.
  - On a stale-edit response, preserve the typed note locally and offer reload.
  - Clear/invalidate the protected coupon cache after a successful update.

This mobile API remains admin-only. Franchisees can currently update codes only
through the authorized web workflow; do not expose the admin endpoint to other
mobile roles.

Sanitized Playwright UI reference:

  docs/mobile-reference/coupon-code-distribution.png

Additional acceptance checks:

  [ ] Distribution metadata survives refetch and app restart.
  [ ] Marking distributed does not change provider redemption status.
  [ ] Empty optional information saves as no note.
  [ ] A stale revision does not overwrite a newer edit.
  [ ] Failed checkbox saves visibly roll back.
  [ ] Non-admin calls still return 403.
