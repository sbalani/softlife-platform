2. DATABASE MIGRATION AND STORAGE
---------------------------------

Migration:

  supabase/migrations/20260814120000_franchisee_remote_permissions.sql

Important terminology correction: there is no franchisee_remote_permissions table. The migration adds this column to public.tenants:

  remote_commands TEXT[] NOT NULL DEFAULT ARRAY['operate_make']::TEXT[]

Therefore permissions are stored once per franchisee tenant, not once per user or machine.

Behavior:

  - Existing and new franchisees default to operate_make.
  - An empty array disables every franchisee remote command.
  - Application code validates values against the configurable command allow-list.
  - There is currently no database CHECK constraint restricting array values.

Production status:

  - Migration 20260814120000 is applied to the linked production database.
  - Defrost/lease migrations 20260814141200, 20260814141300, and 20260814141400 are also applied.
  - Every current production franchisee tenant currently has only [operate_make].


3. FRANCHISEE COMMAND PERMISSIONS
---------------------------------

The commands that an admin may grant to a franchisee are:

  operate_openrefrigeration   Fridge on
  operate_closerefrigeration  Fridge off
  operate_openthawing         Defrost on
  operate_closethawing        Defrost off
  operate_sellout             Sold out
  operate_onsale              Resume sales
  operate_make                Free Cup

Source of truth:

  src/lib/huaxin/remote-commands.ts

Commands outside this configurable list are not available to franchisees, even if an invalid value somehow appears in remote_commands.


4. TEST CUP / FREE CUP
----------------------

The Huaxin command historically called Test Cup is:

  operate_make

The current server label is:

  Free Cup

The behavior is unchanged: it dispenses one free cup. The migration grants operate_make by default to every franchisee.

Mobile should use the command identifier for behavior and render the label returned by GET /commands. Do not hard-code Test Cup as a separate command because it does not exist separately.

operate_make is not safe during an active automated defrost. It will be omitted from GET /commands while defrost is active, and POST will reject it.


5. ADMIN PERMISSION UI
----------------------

Admin UI location:

  /franchisees

Relevant files:

  src/app/(dashboard)/franchisees/RemoteCommandPermissions.tsx
  src/app/(dashboard)/franchisees/actions.ts
  src/app/(dashboard)/franchisees/page.tsx

The UI displays checkboxes for the seven configurable commands on franchisee tenant rows.

Server action:

  setFranchiseeRemoteCommands(tenantId, commands)

Authorization and validation:

  - Requires an admin session.
  - Deduplicates selected commands.
  - Rejects unknown or admin-only commands.
  - Updates only tenants where kind='franchisee'.
  - Revalidates /franchisees and /remote-control.
  - An empty selection is valid and disables all franchisee controls.


6. WEB REMOTE-CONTROL PAGE
---------------------------

Relevant files:

  src/app/(dashboard)/remote-control/page.tsx
  src/app/(dashboard)/remote-control/RemoteControlPanel.tsx
  src/app/(dashboard)/machines/[imei]/actions.ts
  src/lib/data/accessible-machines.ts

Page behavior:

  - Admins and franchisees can open /remote-control.
  - Operators are redirected and cannot use remote control.
  - Admins receive the full backend command catalog.
  - Franchisees receive only the commands granted in tenants.remote_commands and present in the configurable allow-list.
  - Franchisees only see currently assigned, deployed machines.
  - The user must confirm a command before it is sent.
  - The page displays a clear empty state if no controls are granted.

Server action authorization is repeated on the server. A user cannot bypass permissions by modifying the browser UI.

The browser server action checks:

  - User is admin or franchisee, not operator.
  - Franchisee has a tenant_id.
  - Command is configurable and granted to that tenant.
  - Machine has a current date-effective assignment to that tenant.
  - No incompatible automated-defrost run is active.
  - The interactive command lease can be acquired.


7. MACHINE / FRANCHISEE ASSIGNMENTS
------------------------------------

Canonical table:

  public.machine_franchisee_assignments

Relevant fields:

  machine_id
  tenant_id
  start_date
  end_date

Relevant code:

  src/app/(dashboard)/machines/[imei]/assignment-actions.ts
  src/lib/data/accessible-machines.ts
  src/lib/auth/mobile-authorization.ts

Rules:

  - Assignment administration requires an admin session.
  - Date ranges cannot overlap for the same machine.
  - Overlap prevention exists in application validation and a database exclusion constraint.
  - Remote-control authorization queries machine_franchisee_assignments directly.
  - Authorization does not rely on the legacy machines.customer_id field.
  - Mobile evaluates franchisee assignment dates using Europe/Madrid calendar dates.
  - Franchisees can only access deployed=true machines.
  - Admin mobile access is unrestricted by franchisee assignment.

The client must use the machine UUID from /api/softlife/machines, not the IMEI, in the commands endpoint path.


8. MOBILE AUTHORIZATION
------------------------

Authentication header:

  Authorization: Bearer <Supabase access token>

Capabilities:

  - admin: has remote.basic
  - franchisee: has remote.basic
  - operator: does not have remote.basic

The backend rechecks the current profile, role, tenant, assignment, deployment state, tenant command grants, and defrost state on every request. The mobile app must not treat a previously downloaded permission list as permanent.


9. MOBILE API: LIST COMMANDS
-----------------------------

Request:

  GET /api/softlife/machines/{machineUuid}/commands

Success response:

  {
    "machine_id": "machine-uuid",
    "commands": [
      {
        "command": "operate_make",
        "label": "Free Cup",
        "note": "Dispenses one free cup"
      }
    ]
  }

Mobile integration rule:

Always call GET /commands and render the returned list. Do not hard-code role permissions or assume operate_make is always currently available. The response accounts for tenant grants and active defrost restrictions.


10. MOBILE API: SEND COMMAND
-----------------------------

Request:

  POST /api/softlife/machines/{machineUuid}/commands
  Content-Type: application/json
  Authorization: Bearer <Supabase access token>

Body:

  {
    "command": "operate_make"
  }

Success response:

  {
    "ok": true,
    "code": "200",
    "message": "success"
  }

Relevant errors:

  400  Invalid machine ID
  401  Unauthorized
  403  Forbidden, role lacks remote.basic
  403  Command not allowed
  404  Machine not found or not assigned to you
  409  Machine is not available for remote control
  409  Command blocked by an automated defrost or unresolved intervention
  502  Huaxin rejected the command
  502  Command result could not be confirmed
  503  Backend or Huaxin configuration unavailable

If the backend returns HTTP 502 with:

  The command could not be confirmed. Do not retry automatically.

the mobile app must not retry automatically. The machine may have received the command even though confirmation failed.


11. DEFROST SAFETY
-------------------

Only these commands are considered safe while an automated-defrost run is active:

  operate_sellout
  operate_closethawing
  operate_openrefrigeration
  operate_status

Franchisees can only receive the intersection of this safety list and their tenant permissions. operate_status is admin-only, so it is not exposed to franchisees.

All non-safe commands, including operate_make, require an interactive command lease. The lease is refused while an automated run or unresolved intervention owns the machine.


12. AUDIT LOGGING
-----------------

Mobile command attempts are written to public.machine_change_log.

Success or confirmed Huaxin rejection:

  action = remote_command

Transport or unconfirmed failure:

  action = remote_command_failed

Audit metadata includes:

  source = mobile
  role = current user role
  actor ID and email
  machine ID and IMEI
  command identifier

15. KNOWN BACKEND CAVEATS
-------------------------

  - There is no dedicated franchisee_remote_permissions table; permissions are an array on tenants.
  - There is no database CHECK constraint on tenants.remote_commands.
  - Route-level permission tests are still missing.
  - The web server action uses a UTC date for assignment checks, while mobile uses Europe/Madrid. This can differ briefly around midnight.
  - The web command action does not explicitly recheck deployed=true, although the web page only lists deployed machines. The mobile API does enforce deployed=true.
  - The mobile audit insert is best-effort; a command can succeed even if audit logging fails.
