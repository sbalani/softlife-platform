MACHINE MENU READ API (ADDED 2026-08-24)
----------------------------------------

Endpoint:

  GET /api/softlife/machines/{machine_id}/menu

Authentication and authorization:

  - Send the normal mobile Bearer token.
  - The session must include machines.read.
  - The machine must be in the current user's authorized scope.
  - Missing and out-of-scope machines both return HTTP 404.

The endpoint reads the last persisted Huaxin menu snapshot. It never triggers a
live machine sync. A successful response has this shape:

  {
    "machine_id": "uuid",
    "snapshot": {
      "status": "fresh | stale | missing",
      "synced_at": "ISO-8601 timestamp | null",
      "age_seconds": "number | null"
    },
    "menu": {
      "diy": [MENU_ITEM],
      "unify": [MENU_ITEM]
    }
  }

MENU_ITEM fields:

  - id: stable "diy:{position}" or "unify:{position}" identity.
  - kind: "diy" or "unify".
  - position: Huaxin position encoded as a string.
  - name.default: the raw/default Huaxin name, or null.
  - name.translations: object keyed by Huaxin language code.
  - stock: numeric machine counter, or null when absent/non-numeric.
  - enabled: boolean, or null when Huaxin omitted the value.
  - price and market_price: strings to preserve decimal representation, or null.
  - image_url and allergen_url: strings or null.
  - platform_product_id: explicitly persisted platform product UUID or null.

platform_product_id is populated only from machines.base_product_id for DIY
lane 1 and machine_ingredients.product_id for DIY lanes 2-7. It is never
inferred from a menu name. Unified items currently have no persisted mapping.

A missing snapshot returns HTTP 200 with status "missing" and empty arrays.
Snapshots older than 26 hours have status "stale". Cache this response only
within the authenticated identity and scope_version; clear it whenever user ID,
scope_version, role, tenant_id, or capabilities change.

1. RELEASE DECISION
-------------------

Do not start the Android/iOS EAS release builds yet.

The backend date-range route is deployed, and the mobile app typechecks, but
the current mobile implementation has offline-queue, authorization-cache, and
analytics-completeness issues that should be fixed before distribution.

Release-blocking items are sections 2 through 6 below.


2. BLOCKER: OFFLINE QUEUES OVER 50 RECORDS
------------------------------------------

Current mobile behavior:

  src/lib/sync/SyncContext.tsx sends every pending service visit or refill in
  one request.

Backend limits:

  POST /softlife/service-visits/sync accepts at most 50 records.
  POST /softlife/reposicion/sync accepts at most 50 records.

Failure mode:

  If 51 or more records accumulate offline, the backend returns HTTP 400.
  Every retry sends the same oversized batch, so none of the records can ever
  synchronize.

Required mobile change:

  - Split service visits into sequential chunks of at most 50.
  - Split refill-only records into sequential chunks of at most 50.
  - Apply accepted/rejected results after every successful chunk.
  - Stop on a transient/network failure and leave only unsent records pending.
  - A permanent rejection in one chunk must not corrupt accepted records.
  - Add automatic retry with bounded backoff while the device remains online.

Acceptance tests:

  [ ] 51 refill-only records synchronize as 50 + 1.
  [ ] 51 combined service visits synchronize as 50 + 1.
  [ ] An error in the second chunk does not resend the accepted first chunk.
  [ ] A transient failure retries without requiring another outbox change.


3. BLOCKER: CATALOG CACHE IS NOT SCOPE-VERSIONED
------------------------------------------------

Current mobile behavior:

  HTTP response cache keys include scope_version.
  SQLite machines and lots are keyed only by owner_user_id.
  AuthContext clears the catalog when the user ID changes, but not when the
  same user's scope_version, role, tenant, or capabilities change.

Failure mode:

  A user can lose a machine assignment, receive a newer scope_version, fail to
  refresh while offline, and still see/use the machine and lots from the old
  scope. The backend will eventually reject submitted work, but the mobile app
  should not offer unauthorized cached operations in the first place.

Required mobile change:

  Choose one safe approach:

  A. Store scope_version with machine/lot rows and query by user + scope; or
  B. Clear machines, lots, and protected response caches before applying a
     session where scope_version, role, tenant_id, or capabilities changed.

  Do not retain old-scope catalog rows when the new-scope refresh fails.

Acceptance tests:

  [ ] Same user ID with incremented scope_version cannot read old machines.
  [ ] Assignment removal while offline does not expose old machine actions.
  [ ] Role/capability downgrade clears protected cached data.
  [ ] Account switching never displays the previous account's data.


4. BLOCKER: TERMINAL AUTHORIZATION FAILURES
-------------------------------------------

Current mobile behavior:

  AuthContext treats refresh HTTP 401 as terminal but treats HTTP 403 as a
  transient failure and restores/retains the cached session.

Backend behavior:

  POST /softlife/auth/refresh returns HTTP 403 when the Supabase user exists
  but the SoftLife profile is missing or no longer valid.

Failure mode:

  A removed/disabled profile remains locally authenticated with its old role,
  capabilities, token, and offline catalog.

Required mobile change:

  - Treat refresh HTTP 401 and 403 as terminal.
  - Atomically clear SecureStore session, protected SQLite cache, and React
    Query data on terminal authorization failure.
  - For ordinary API 401 responses, attempt one single-flight token refresh
    and retry the request once.
  - If refresh fails with 401/403, log out atomically.
  - Do not retry API 401/403 through React Query's generic retry policy.

Acceptance tests:

  [ ] Startup refresh 403 clears the local session.
  [ ] Scheduled refresh 403 clears the local session.
  [ ] Concurrent API 401 responses perform only one refresh request.
  [ ] Failed refresh clears protected Query and SQLite data.


5. BLOCKER: LOGOUT / IN-FLIGHT CACHE RACE
-----------------------------------------

Current mobile behavior:

  Logout clears SQLite but does not cancel React Query requests or remove the
  process-wide QueryClient data. A request that finishes after clearCatalog()
  can write the old user's response back into SQLite.

Required mobile change:

  - Cancel active protected queries before clearing local data.
  - Remove protected/all QueryClient data during logout and account switch.
  - Add an auth/session generation check before fetchCached writes SQLite.
  - Ensure a response belonging to an old session cannot update state/cache.

Acceptance tests:

  [ ] Logout racing an in-flight fleet request leaves no response cache rows.
  [ ] Logout racing catalog refresh cannot repopulate machine/lot data.
  [ ] Logging into another account cannot reveal the previous account's data.


6. BLOCKER: ANALYTICS RANGE COMPLETENESS
----------------------------------------

Backend route now deployed:

  GET /softlife/admin/orders?from=YYYY-MM-DD&to=YYYY-MM-DD

Production verification:

  Backend commit 84208e0 is deployed successfully.
  The route exists and returns 401 without authentication.
  Production currently stores 703 orders from 2026-07-01 onward.

Important limitation:

  The sync object returned by getOrders describes the latest fleet sync, not
  guaranteed coverage of the selected analytics range.

  Current production sync runs cover only yesterday and today. Pulling the
  30-day view does not backfill all 30 days. Historical records already in the
  database are returned, but late-uploaded historical sales may be missing.

Current mobile problem:

  The screen only checks sync.status and failedMachines. It can show a 7-day or
  30-day range as complete even when sync.requestedFrom/requestedTo cover only
  two days.

Required mobile change now:

  - Verify response date_from/date_to exactly match the requested range.
  - If they do not match, do not calculate/display confident range totals.
  - Compare sync.requestedFrom/requestedTo with the selected range.
  - Show an explicit historical-coverage warning whenever the sync range does
    not cover the selected range.
  - Defensively filter returned orders to the requested Europe/Madrid dates.
  - Do not claim that pull-to-refresh backfilled the selected historical range.

Backend follow-up:

  The platform should add explicit range coverage metadata and/or a controlled
  historical backfill operation. Until then, the mobile warning is required.

Acceptance tests:

  [ ] Response range mismatch is detected and visibly reported.
  [ ] 30-day selection with a two-day sync shows incomplete-coverage warning.
  [ ] Orders outside the requested Madrid range do not affect metrics.
  [ ] Madrid midnight and DST boundaries are covered by tests.


7. PULL-TO-REFRESH MUST NOT RUN FULL FLEET SYNC
-----------------------------------------------

Current mobile behavior:

  Pull-to-refresh on Analytics and Fleet calls POST /softlife/admin/sync.

That endpoint performs a fleet-wide Huaxin operation: device status, menus,
media, temperatures, coupons, orders, and alert notifications. It can take up
to five minutes and currently synchronizes only yesterday/today orders.

Required mobile change:

  - Pull-to-refresh should call React Query refetch only.
  - Keep full upstream synchronization as a separate, explicit, clearly
    labeled admin action with confirmation/progress.
  - Do not imply that full sync refreshes a selected 7/30-day historical range.


8. CACHE RETRY, INVALIDATION, AND RETENTION
-------------------------------------------

Required improvements:

  - Use a network-state listener rather than only 30-second polling so pending
    writes and cached queries resume promptly on reconnect.
  - Add bounded retry/backoff for transient outbox failures while online.
  - After successful coupon create/delete, invalidate or update the disk cache
    before fallback can restore the known-stale pre-mutation list.
  - Add TTL/retention limits for cached_responses. Date-keyed analytics entries
    currently accumulate indefinitely.
  - Keep 401/403 excluded from offline fallback.

Acceptance tests:

  [ ] Reconnect triggers prompt query refetch and outbox synchronization.
  [ ] Successful coupon deletion cannot reappear from stale disk cache.
  [ ] Old date-range cache rows are evicted by documented policy.


9. ANALYTICS PRESENTATION CORRECTIONS
-------------------------------------

Required mobile changes:

  - Format order and sync timestamps using data.time_zone (Europe/Madrid), not
    the phone's local timezone, or explicitly label them as device-local.
  - Rename "Pedidos" to "Pedidos netos" because the metric excludes refunded
    and admin-override completed orders; alternatively show separate counts.
  - Zero-sales days should render zero-height/empty bars, not a 3-pixel sale.
  - Do not group different machines by the same fallback display name when
    device_imei is missing. Use a stable identifier when the API provides one,
    or label those records as ungrouped.


10. BACKEND RANGE CONTRACT NOTES
--------------------------------

Current supported requests:

  GET /softlife/admin/orders?date=2026-08-15
  GET /softlife/admin/orders?from=2026-08-09&to=2026-08-15

The date range is inclusive, Europe/Madrid, and limited to 90 days.

Mobile should always send both from and to for a range. Do not mix date with
from/to and do not send only one range bound.

Mobile should require:

  response.date_from === requested from
  response.date_to === requested to
  response.time_zone === Europe/Madrid


11. TEST COVERAGE REQUIRED
--------------------------

Typecheck and Expo export are useful but do not verify cache/auth correctness.

Add focused automated tests for:

  - scope_version catalog isolation.
  - fetchCached fallback and mutation invalidation.
  - Cache TTL/eviction.
  - Madrid date range generation and DST boundaries.
  - Analytics range-response mismatch.
  - Refund/admin-override metric semantics.
