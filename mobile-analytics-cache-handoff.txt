2. BACKEND CONTRACT REQUIRED BY MOBILE
---------------------------------------

Endpoint:

  GET /api/softlife/admin/orders

Authentication and authorization:

  Authorization: Bearer <Supabase access token>
  401 when the token is missing or invalid.
  403 when the authenticated user is not an admin.

Backward-compatible single-day request:

  GET /api/softlife/admin/orders?date=2026-08-15

New date-range request:

  GET /api/softlife/admin/orders?from=2026-08-09&to=2026-08-15

Rules:

  - from and to use YYYY-MM-DD.
  - Dates are interpreted as Europe/Madrid calendar dates.
  - The range is inclusive.
  - from must not be after to.
  - The maximum inclusive range is 90 days.
  - Invalid or impossible dates return HTTP 400.
  - Omitting all date parameters retains the existing current-day behavior.

Success response additions:

  {
    "date": "2026-08-09/2026-08-15",
    "date_from": "2026-08-09",
    "date_to": "2026-08-15",
    "time_zone": "Europe/Madrid",
    "sync": null,
    "orders": []
  }

The existing order object shape is unchanged. date remains for compatibility;
date_from and date_to describe the normalized range. A single-day response may
continue returning date as YYYY-MM-DD.


3. BACKEND IMPLEMENTATION IN THIS CHANGE
----------------------------------------

Relevant file:

  src/app/api/softlife/admin/orders/route.ts

The route change included with this handoff:

  - Preserves the date query parameter.
  - Adds inclusive from/to parameters.
  - Validates real calendar dates and a maximum 90-day range.
  - Calls getOrders once with dateFrom/dateTo and DEFAULT_TZ.
  - Returns date_from and date_to without changing order records.

No Supabase migration is required. The existing getOrders implementation
already supports dateFrom/dateTo and filters records by the requested timezone.

7. BLOCKER COMPLETION STATUS
----------------------------

Section 2 - Offline queues over 50 records: completed.

  - Combined service visits and refill-only records are sent sequentially in
    chunks of at most 50.
  - Every successful chunk is validated and committed before the next starts.
  - Accepted/rejected combined rows are updated atomically in SQLite.
  - A failed later chunk leaves earlier accepted work settled and unsent work
    pending.
  - Transient failures retry after 1, 2, 4, 8, and 16 seconds while online.
  - Reconnect and new enqueue events reset the bounded retry cycle.
  - Protocol-invalid responses stop without applying or repeatedly retrying
    the affected chunk.

Section 3 - Catalog authorization scope: completed using approach B.

  - Authorization identity includes uid, scope_version, role, tenant_id,
    employer_kind, and sorted capabilities.
  - Any authorization identity change rotates the process session generation
    and clears machines, lots, protected response cache, and QueryClient data
    before publishing the replacement session.
  - Catalog/cache reads and writes are generation guarded.
  - Protected writes and clears share a serialized queue, preventing an old
    request from repopulating SQLite after logout or account/scope transition.

Section 4 - Terminal authorization failures: completed.

  - Refresh HTTP 401 and 403 are terminal.
  - Ordinary protected API 401 responses use one shared refresh flight and
    retry the original request once with the replacement token.
  - Concurrent API 401 responses share the same refresh request.
  - Query generic retry excludes 401, 403, aborts, stale sessions, stale cache
    operations, and analytics contract mismatches.
  - SecureStore now uses one versioned session envelope and migrates legacy
    token/user keys.
  - Terminal cleanup blocks protected UI until SecureStore, SQLite, and
    QueryClient cleanup succeeds; failed native cleanup operations retry.

Section 5 - Logout/in-flight cache race: completed.

  - Session generation invalidates stale work before asynchronous cleanup.
  - Active queries are cancelled and the process QueryClient is cleared.
  - Protected SQLite writes are serialized with clears and check generation.
  - Query keys include session generation.
  - Push display is disabled until the current session's Expo token POST
    succeeds. Logout clears pending notification responses and visible
    notifications. The backend's expo_push_token upsert reassigns the unique
    device token when a later account registers.

Section 6 - Analytics range completeness: completed.

  - Mobile always sends both from and to.
  - A response is accepted/cached only when date_from, date_to, and
    time_zone exactly match the requested Europe/Madrid range.
  - A mismatched response never falls back silently and hides aggregate totals.
  - sync.requestedFrom/requestedTo are checked for complete selected-range
    coverage and an explicit historical completeness warning is shown.
  - Every returned order is defensively filtered by its Europe/Madrid calendar
    date before totals, charting, ranking, recent-order display, or empty state.
  - Pull-to-refresh explicitly states that it does not backfill history.


8. ADDITIONAL REVIEW ITEMS
--------------------------

  - Fleet and Analytics pull-to-refresh now perform lightweight query refetch
    only.
  - Full Huaxin fleet synchronization remains a separate confirmed admin
    action on Fleet, with an up-to-five-minute warning and no historical
    backfill claim.
  - expo-network addNetworkStateListener replaces 30-second polling and drives
    React Query reconnect plus outbox retry.
  - Accepted partial outbox progress triggers query invalidation and a separate
    bounded catalog-refresh retry, even if a later chunk fails.
  - Coupon create/delete rotates the per-key disk-cache epoch and cancels the
    current query before invalidation. Deletion updates memory optimistically;
    creation hides the old list until a genuinely newer successful fetch.
  - cached_responses has a seven-day fallback TTL, global expiry pruning, and
    a maximum of 100 newest entries per user.
  - Timestamps use Europe/Madrid on analytics and machine sales views.
  - Labels say Pedidos netos where refunds/admin overrides are excluded.
  - Zero-sales chart bars have zero height.
  - Orders without a stable IMEI are kept ungrouped by order ID rather than
    merged by display name.

Endpoint:

  GET /api/softlife/machines/{machineUuid}/status

Authentication and authorization:

  - Requires a valid Supabase bearer token and machines.read.
  - Uses the same mobile machine-assignment scope as GET /api/softlife/machines.
  - Invalid UUIDs return 400; missing or unassigned machines return 404.
  - The response does not include sales, orders, IMEI, or raw Huaxin payloads.

Freshness behavior:

  - A snapshot older than one minute triggers a scoped Huaxin refresh for only
    the requested, authorized machine.
  - A failed Huaxin refresh retains the last observed status rows.
  - status_stale becomes true when the newest observation is over two hours old
    or no usable observation time exists.
  - Statuses are translated, deduplicated by code, and presented in operational
    priority order.

Mobile behavior:

  - The normal /machine/[id] page displays current statuses as responsive cards.
  - Statuses refresh when the page receives focus and on pull-to-refresh.
  - The page shows the observation time and warns when the snapshot is stale.
  - Online/normal states, shortages, and actionable cup faults use distinct
    visual tones.
